# HAnumans — サイト構想

> **ブランド名：HAnumans**（正式決定）
>
> **Once you enter the HA jungle, there's no way out.**
>
> 日本語コピー案：**HAに沼った人々**

## コンセプト

Home Assistantで実現できること、工夫したこと、発見したことを共有し、次のアイデアにつなげる場所。

単なる自動化レシピ集や網羅的なマニュアルではなく、「こんなこともできるんだ」「自分の家でも試してみたい」と発見するためのサイトを目指す。読むだけの人も、事例を追加する人も、みんなHAの沼に入った仲間＝HAnumans。

ブランド名は **HAnumans** に正式決定。ロゴは引き続き検討中。

## コンテンツ方針

内容を細分化しすぎず、大まかな入口を用意する。網羅性を追い求める百科事典にはしない。詳細な手順や仕様は公式ドキュメントなど外部の資料へ案内する。

想定する大分類（今後調整）:

- **事例 (Cases / Use cases)** — Home Assistantで実現する具体的なアイデアや使い方。
- **ダッシュボード (Dashboards)** — 構成や考え方、代表的な例を簡潔に紹介。Lovelaceの詳細ガイドにはせず、カード・レイアウト等は外部資料を案内する。
- **トリガー (Triggers)** — 自動化のきっかけになる状態・イベント・条件の解説。
- **アクション (Actions)** — HAで実行できること、機能や操作の紹介。
- **デバイス (Devices)** — センサー、スイッチ、コントローラーなどの機器。
- **ネットワーク・通信 (Network)** — Wi-Fi、Zigbee、Matterなど通信方式や連携技術。
- **Integration / HACS / Marketplace** — 目的に応じて役立つ連携、カスタムカード、Blueprint、アドオン等の発見を支援。網羅的な一覧ではなく「やりたいこと→役立つツール」の視点で紹介。
- **基礎知識 (Concepts)** — HAを理解するための基本概念・用語。

分類は暫定。必要に応じて追加・統合・名称変更する。

## 事例の分類とタグ

事例では、従来の単一カテゴリに代えて、以下の分類を検討する。

- `event_category`: 何が起きたか／何をきっかけにするか
- `action_category`: 何を実行するか／何をしたいか
- `tags`: 記事に関連する自由なタグ

分類値やタグは記事のMarkdown側で定義し、サイト側で内容から値を自動収集して一覧・タグページを生成する方向。

- 値をコードに固定しない。新しい値も記事追加で生まれる仕組みを目指す。
- ChatGPTで新しい事例を作る際は、既存タグ・カテゴリの一覧を確認し、なるべく既存語を再利用する。新語が必要なら提案する。
- 表記揺れや重複（例：「照明」「ライト」）は起こり得る。サイト管理者が後から整理・統合する。分類の完全性より、追加しやすさと管理のしやすさを優先する。
- タグやカテゴリはクリックできる形で表示し、関連する記事を探せるようにする。

## ディレクトリ構成\n\nコンテンツとプログラムをリポジトリのトップレベルで分離する。記事追加者が編集対象を直感的に理解できるよう、Markdownコンテンツはトップレベルの `content/` に置き、サイトを構築するコードは `src/` に置く。\n\n`content/` 以下の分類：\n\n- `triggers/`\n- `actions/`\n- `use-cases/`\n- `devices/`\n- `networks/`\n- `integrations/`\n- `apps/`\n\n`src/` はサイトのプログラム専用とし、`pages/`、`layouts/`、`components/`、`styles/` などを配置する。AstroのContent Collections設定は外部の `content/` ディレクトリを参照する。\n\n## Markdownを中心にした追加・編集

新しい事例や解説を追加する基本手段はMarkdownファイルとする。個々の記事のためにコードを編集する必要がない構成を目指す。

記事作成時の想定フロー:

1. 既存のカテゴリ・タグの一覧を確認する。
2. 既存の語彙を優先して選び、新しい語が必要なら提案する。
3. 記事をMarkdownで作成する。
4. サイトが分類値・タグを集約し、一覧ページや関連リンクを自動生成する。
5. 必要に応じて管理者が語彙を手動で統合・修正する。

## 多言語化とURL

将来的に海外からも利用できるようにすることを視野に入れ、URLには初めから言語コードを含める方針を検討する。

例:

- 日本語: `/ja/`, `/ja/cases/`, `/ja/cases/arrival-light/`
- 英語: `/en/`, `/en/cases/`, `/en/cases/arrival-light/`

日本語もルート直下の既定言語扱いにせず、明示的に`/ja/`を使う。各言語のコンテンツは分離し、同一記事の翻訳が存在する場合は言語切替から対応記事へ移動できるようにする。翻訳がない場合は、その言語のトップまたは一覧へ案内する。

slug（URL末尾の識別子）は、可能なら言語間で共通にする。slugはタイトルのローマ字化ではなく、内容を表す短い英単語・英語表現を使う。記事タイトルや本文は各言語で自然に翻訳する。公開後のslugは原則変更しない。URL構成を移行する場合は既存URLからのリダイレクトも検討する。

## HACS / Marketplace等の紹介方針

外部ツールや拡張機能を網羅するカタログにはしない。目的別に選択肢を発見できるようにする。

例:

- 標準では取得できない情報がほしい → Integration
- ダッシュボードを見やすくしたい → Custom Card
- グラフを強化したい → Graph系カード
- 特定機器を制御したい → Integration（公式／HACSなど）
- 通知を便利にしたい → Integration / Blueprint

紹介は公式ドキュメント、GitHub等の一次情報へのリンクを中心にする。
